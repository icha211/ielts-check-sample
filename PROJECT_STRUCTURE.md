# Non-Breaking Project Structure

This repository now uses an additive structure for future AI work.

Current production-like website flow remains unchanged:

- Root HTML pages stay at the repository root.
- `toefl-sample/` stays in place.
- `ai_review_server.py` stays in place.
- `data_storage_server.py` stays in place.
- Existing `storage-sync.js` and `toefl-sample/toefl-storage-sync.js` stay in place.

These files are still the active website/runtime surface. Do not move them until a dedicated migration phase is planned and the relative paths are updated together.

## Frontend deployment boundary

Firebase Hosting and GitHub Pages publish only `.public-site/`, generated by
`python infra/stage_public_site.py`. Firebase runs this as a Hosting predeploy hook;
Pages runs it before uploading its artifact. For local Hosting emulation, run it
before starting the emulator and again after frontend changes.

The staging allowlist preserves root HTML/JS/CSS and static assets under `asset/`,
`asst/`, and `toefl-sample/` at their existing relative URLs. Backend code, credentials,
configuration JSON/YAML, documentation, test scripts and logs are not published.
New public directories or file types must be added to the allowlist and tested.
The `/api/**` Cloud Run rewrite is unchanged.

## Shared content save reliability

Shared Firebase PUT requests use ETag/If-Match conditional requests. A stale editor is
rejected rather than overwriting newer content; reload the affected editor before
retrying. TOEFL draft saves return `false` on cloud failure while retaining the
local draft. Metadata saves reject on failure, and imports merge individual
records instead of replacing a whole catalog. An import can partially succeed;
its failure must not be displayed as fully synced.

Legacy `storage-sync.js` problem CRUD retries revision conflicts against fresh
remote data, retaining other additions and modules. Bulk replacement requires a
successful preceding read and rejects stale revisions. Failed writes never count
as cloud success, and existing database permissions remain unchanged. The legacy
IELTS problem path is still denied by the checked-in rules; this change does not
make that legacy surface publicly writable.

Run `node --test storage-sync.test.js` for mocked concurrency and failure tests.
These tests do not replace live Firebase/rules-emulator or recovery validation.

## AI private-beta boundary

`apps/api-gateway/ai_runtime.py` shares authentication-aware, transactional Firestore
quotas and bounded provider calls with the root legacy AI/transcription servers.
The gateway chat/evaluation routes now call that runtime instead of returning stubs.
Browser chat uses `toefl-sample/ai-client.js`, not a provider key. AI is disabled
until both its environment enable flag and trusted Firestore control are configured.
See `apps/api-gateway/README.md` for limits, deployment prerequisites and the
recorded-results DeepSeek benchmark gate. Provider migration is not automatic.

## Local private-beta validation

Install the declared root test dependencies with `npm ci`, then install the
test browser with `npx playwright install chromium` (Linux CI also uses
`--with-deps`). In an isolated Python environment, install `requirements.txt`.
Run `npm run test:beta` from the repository root. It stops on the first failed
layer: gateway authentication/provider/quota tests, frontend unit/submission
tests, then Playwright desktop (1280px) and mobile (390px) journeys.
Individual layers use `npm run test:beta:unit` and `npm run test:beta:browser`.

The browser suite uses actual signup, marketplace, history and review pages,
real course model/service logic and real history/AI clients. Firebase SDK and
AI HTTP boundaries are replaced with local synthetic accounts, data and
responses. Peripheral navbar notifications/account menus and CDN resources
are mocked; these are not covered by this suite. Practice submit-handler tests
run in the unit layer; browser history tests start at the real result-recording
API, not the full timed practice-taking journey.
Inline outcome/lesson display rows retain the input's 44px minimum height so
leaving an edit does not collapse the row underneath an in-progress button click
on mobile. The course-creation browser journey covers this interaction.

Playwright owns the localhost-only server on port 9460 and stops it after the
run. It will not reuse another process on that port. The server serves only
frontend-allowlisted assets, never credentials, backend files or directory
listings. Browser contexts are isolated per test; no real Firebase writes,
accounts, credentials or paid AI requests are used. Failure traces live in
ignored `test-results/beta/`; CI retains them for seven days. Test infrastructure
and reports remain excluded from Hosting/Pages artifacts.

Passing this suite is a local regression gate, not launch certification.
Before opening a live beta, still revoke previously exposed credentials,
deploy verified configuration/rules, run staging account and permission flows,
validate monitoring/restore/load behavior, and complete real provider quality
benchmarking before approving DeepSeek.

### Opt-in live permission validation

`infra/live_beta_validation.py --execute` is a separate operational check, never
part of CI or `npm run test:beta`. It targets `quickcheck-25590` only and requires
explicit permission to temporarily create synthetic Firebase accounts and data.
Supply a short-lived operator OAuth access token via `BETA_ADMIN_TOKEN` in the
process environment, never a command argument, saved file or chat message.
Admin Auth requests specify `X-Goog-User-Project` for the target project.

The script verifies deployed RTDB rules against the repository and requires
the serving gateway revision to have AI disabled before making authenticated
requests. Three disposable accounts exercise real password login, marketplace
role restrictions, course ownership/update/archive, private history isolation,
registered-account AI denial and teacher/developer separation. Test courses
are unpublished and never use existing practice packages.

Cleanup deletes only exact run-specific paths and accounts, then checks their
absence, including derived teacher identities/course statistics. A failed check
or unconfirmed cleanup exits unsuccessfully. This REST-level test complements
the mocked browser suite; it does not prove live browser SDK hydration or
Firebase Storage permissions. It does not inspect/export user data, restore
backups, enable AI, change rules, or validate paid-provider quotas.

The Explore composer uses a single post-body field without a separate title.
Explore's **Recommended** sort implements the uploaded algorithm design with
Following (accepted, reciprocal message connections) and Global modes.
Each ten-item cycle targets 60% primary posts, 20% discovery/network posts,
10% practice partners, and 10% published courses. Empty pools borrow other
eligible items without duplicates. Own posts are a last-resort Following fill,
not a followed-account quota. Chronological/most-liked sorts and profile/group
views preserve the existing post-only browsing behavior.

`getExploreFeed` samples up to 100 public posts, connections, discoverable
practice profiles, directory profiles, and published courses; up to 30 private
posts per accepted connection in Following; and up to 200 likes/comments/signal
accounts per public post. It returns up to 30 mixed items. Weights are view 5,
save 4, share 3, comment 2, like 1; social-network weights omit views. Existing
likes/comments are read directly, so they do not require a historical backfill.
Saves, shares and qualifying views count once per account/post, while each
sampled comment counts. Learning interest sums these weights for a post's
selected topics; course categories match the same topics.

Teachers/learners can choose up to three of the document's 40 post keywords.
Practice matching is 40% goals, 30% proficiency, 20% skills, 10% learning styles;
multi-select fields use intersection divided by union. Missing fields score zero.
Practice preferences remain private unless the learner opts into discovery;
hidden partner-directory profiles are not recommended. Viewing personalization
is separately opt-in and off by default. The client records a post only after
more than ten seconds of continuous visible, foreground viewing, or at video
foreground video completion with at least 95% played. Blurring/hiding the page
or refreshing its ranked cards resets pending dwell time. Disabling it stops new events and excludes
prior view signals from that learner's interest score; historical aggregate
engagement remains. Client-reported viewing is an interest hint, not proof of
attendance, watch completion, payment, or a reward entitlement.

Friends-only posts and their engagement never enter Global recommendations.
Blocked accounts in either direction are excluded on the backend. Signals and
discovery records are server-only, and own preferences/actions are
owner-readable. Callables require registered, email-verified accounts.
Limits per account/hour: 60 feed requests, 30 preference saves, 240 explicit/view
interaction requests. Ranking refresh is on demand, with one-minute manual
refresh spacing and five maximum function instances; no paid AI/ranking service
or polling job is added. Live post CRUD/activity remains Firebase realtime.
Failed ranking visibly falls back to accessible chronological posts with Retry.

and random 96-bit IV. Only ciphertext is uploaded to
`community-private/<uid>/<post>/attachment`; the key, IV and original MIME type
are stored in the friend-protected post. Download links alone cannot decrypt
these attachments. Decrypted object URLs are revoked when posts leave the feed
or the account changes. Friends can save or share content they already received;
removing a friendship cannot erase their copies. This is not end-to-end
encryption against the database operator. Deploy both database and Storage
rules before using the new audience controls.

Only authors can edit
posts; authors and verified developers can remove posts/comments. Announcements
are developer-only. Removed posts are retained but hidden and cannot receive new
comments or likes.

New attachments are PNG, JPEG or WebP only. Source images up to 40 MB are
compressed in the browser to at most 2 MB before upload; friends-only media is
encrypted and stored as ciphertext with up to 16 bytes of AES-GCM overhead.
Public files are stored at `community/<uid>/<postId>/attachment`, and private
ciphertext at `community-private/<uid>/<postId>/attachment`. Post edits preserve
existing attachments. Uploads that fail to publish are cleaned up. Publish
**the Database rules, Storage rules and callable Functions before using the new page**:

```powershell
firebase deploy --only database,storage,functions
node --test toefl-sample\community.test.js
```

`community-rules.test.js` additionally runs when
`FIREBASE_DATABASE_EMULATOR_HOST` is set; use the `demo-toefl-messaging` emulator
project to run it alongside the existing messaging-rule tests. Run both rule
emulators locally with:

$env:FIREBASE_DATABASE_EMULATOR_HOST = "127.0.0.1:9450"

4. Shared contracts should be defined before replacing the current review/storage endpoints.
